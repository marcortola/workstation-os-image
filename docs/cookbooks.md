# Cookbooks

Copy-paste recipes for the changes people actually make to this image. Each one
states when to use it, the steps, and the command that proves it worked. It
assumes you have read [conventions.md](conventions.md) — the reasoning behind
each mechanism lives there, and is not repeated here.

**Every change belongs to the smallest durable owner that can still recreate it
on a fresh machine.**

---

## Choosing an owner

Decide this first. Picking the wrong owner is how a change ends up living only
on the live machine.

| The change is... | It belongs in | Recipe |
|---|---|---|
| An RPM, daemon, socket, privileged helper or system preset | `build_files/` or `system_files/` | [RPM](#add-an-rpm-to-the-image), [unit](#add-a-systemd-unit), [`/etc` file](#ship-an-image-owned-file-into-etc) |
| A Homebrew formula, cask or Flatpak | `~/.config/homebrew/Brewfile`, then `just sync` | [Homebrew and Flatpak](#add-a-homebrew-formula-cask-or-flatpak) |
| Portable user configuration | one entry in `tooling/data/dotfiles.manifest`, then `just sync` | [dotfile](#capture-a-new-portable-dotfile) |
| A niri customisation | `~/.config/niri/local.kdl` — never `config.kdl`, never a `dms/` fragment | [keybind](#add-or-reclaim-a-niri-keybind) |
| A DMS preference | change it in the GUI, then `just dms-capture` | [DMS default](#promote-a-dms-preference-to-a-workstation-default) |
| A secret, token, credential or device-specific runtime state | nowhere in Git — document the setup command instead | — |

One rule cuts across all of them. Generated output is never hand-edited: the
manifest-captured seeds under
`system_files/usr/share/workstation-os-image/dotfiles/` are overwritten wholesale
by `just sync`, and `tooling/ai/ai-cli-setup/` is regenerated by
`just ai-bundle`. Change the live file, then regenerate. The exception is a
`scaffold` manifest entry, which is image-owned, hand-edited in the repo, and
never captured from live — `tooling/dotfiles/sync` has an empty `scaffold)` case
for exactly that reason.

> Never weaken, delete or add an exception to a gate to make a run pass. The
> hand-written gates in `tooling/validate/` are the real secret boundary —
> gitleaks misses tool-specific key shapes. If a gate is genuinely wrong, say
> so and stop.

## Add an RPM to the image

**When:** the package is an OS-level dependency — a daemon, a library the
desktop imports at runtime, a compiler, a tool that must exist before `$HOME`
does. Anything you could equally install with Homebrew belongs in the
[Brewfile](#add-a-homebrew-formula-cask-or-flatpak) instead.

1. Pick the list under `build_files/packages/` that matches the concern. Each is
   one dnf transaction, so a failure names the group rather than dumping one
   200-package error:

   | List | Holds |
   |---|---|
   | `desktop.list` | compositor, shell, session — niri, greetd, foot, fish, btop, chezmoi |
   | `dev.list` | toolchain and CLI; Homebrew needs a linker and compiler for source builds |
   | `docker.list` | rootful Docker and containerd |
   | `copr.list` | the DMS/danklinux COPR stack |
   | `terra.list` | the Terra allowlist — uupd, satty, iio-niri, maple-fonts |
   | `media.list` | negativo17 codec additions |
   | `qt-style.list` | the Qt/QML modules quickshell imports but does not declare |
   | `input-method.list` | the fcitx5 stack |
   | `fonts.list` | font packages |
   | `insync.list` | insync |

2. Add the package name, one per line. A trailing `# comment` is stripped by
   `20-packages.sh`, so use it to record which repo the package comes from and
   why it is here.
3. If the package must never be installed even as a transitive dependency, it
   goes in `exclude.list` instead. That list is turned into `--exclude=` flags
   applied to *every* transaction — it exists because negativo17's
   `gstreamer1-plugins-bad` drags in 186 MiB of fluidsynth soundfont samples
   nothing on this image uses.
4. If the package is load-bearing enough that its silent absence would produce a
   working boot and a broken desktop, add it to the presence loop in
   `build_files/99-check-build.sh`.

**Verify.** Check the built image, not the source tree — the list is an
instruction, not a result. The `review-` tag is what `just build` produces
(`IMAGE_NAME` comes from `image.env`):

```bash
just build
podman run --rm \
    "localhost/workstation-os-image:review-$(git branch --show-current | tr / -)" \
    rpm -q <package>
```

The image also bakes a sorted NEVRA manifest at
`/usr/share/workstation-os-image/package-manifest.txt`, which CI diffs against
the published `:latest`. See [build-and-ci.md](build-and-ci.md).

## Add a third-party repository and its signing key

**When:** the package you need is not in Fedora, negativo17, Terra or the COPRs
already vendored.

Repositories are vendored, never fetched. A remote repofile's `baseurl` and
`gpgkey` silently become the build's trust anchors on whatever day it runs; a
committed file puts both under `git diff` and gitleaks.

1. Write `build_files/repos/<name>.repo` by hand. Four properties are gated by
   `tooling/validate/image-build`, which runs in `repo-gates` before anything is
   built, so a missing one fails the pull request:

   ```ini
   [example]
   name=Example $releasever
   baseurl=https://packages.example.com/fedora/$releasever/$basearch
   gpgcheck=1
   gpgkey=file:///etc/pki/rpm-gpg/example.asc
   enabled=1
   includepkgs=only,the,packages,you,want
   ```

   `gpgcheck=1`, a `file://` gpgkey, an `https` `baseurl` or `metalink`, and an
   `includepkgs` allowlist. The allowlist is not theoretical; the incident that
   put it there is in [subsystems/packages.md](subsystems/packages.md).
2. Fetch the upstream key once, review it, and commit it as
   `build_files/keys/rpm/<name>.asc`. `10-repos.sh` installs every `*.asc` into
   `/etc/pki/rpm-gpg/` and `rpm --import`s it *before* dnf reads any repo file,
   because each repo references its key by path.
3. Record its provenance in `build_files/keys/rpm-key-sources.json` — the
   fetch URL, the full fingerprint, and the key uid.
4. Add the key basename to the vendored-key loop in
   `build_files/99-check-build.sh` (`for k in copr-yalter-niri ... insync`), so
   the build fails if the key stops shipping.
5. Add the packages to a list under `build_files/packages/` (see the recipe
   above). `90-cleanup.sh` deletes every non-Fedora, non-negativo17 repo file
   from the shipped image, so a new repo is automatically build-time only.

**Verify:**

```bash
tooling/validate/image-build   # the four-way fence on every .repo
tooling/validate/rpm-keys      # fingerprint match, then upstream byte-identity
just build
```

`tooling/validate/rpm-keys` re-fetches each URL from the manifest and compares.
A rotated key upstream fails the gate so you review it, rather than silently
changing what the build trusts. See [supply-chain.md](supply-chain.md).

## Add a Homebrew formula, cask or Flatpak

**When:** the tool is a user-space CLI or a desktop application. This is the
default answer for anything that does not need to exist before login.

1. Edit the **live** file, `~/.config/homebrew/Brewfile`. It is captured by the
   manifest line
   `copy|.config/homebrew/Brewfile|dot_config/homebrew/create_Brewfile|-`, so
   the repo copy is generated — editing the seed directly is reverted by the
   next `just sync`.
2. Use `brew "name"`, `cask "name"` or `flatpak "app.id"`. A tap-qualified line
   such as `brew "satococoa/tap/git-worktreeinclude"` is self-trusting: no
   separate `tap` line is needed.
3. Install it: `brew install <name>` (or `just brew-apply` to install every
   not-yet-installed entry at once).
4. `just sync` to refresh the seed, then commit.

Never add **btop**, **chezmoi**, **Git**, **fzf**, **Just** or **Fish**. The
image ships btop, chezmoi and fish from `build_files/packages/desktop.list`
(`fish  # the image owns /usr/bin/fish; never install via brew`), and base-main
ships Git, fzf and Just. Known shadows already installed are listed in
`tooling/data/image-provided-brew-formulae` so `tooling/audit/packages` reports
them as `image-shadow` rather than as undeclared packages.

**Verify:**

```bash
just audit    # tooling/audit/packages compares installed vs declared
```

An undeclared formula or cask is an error; an undeclared Flatpak is a warning,
because a workstation may legitimately keep host-only Flatpaks. On a machine
that already has the image deployed, a newly declared entry is not installed
until you run `just brew-apply` once — a tap-qualified line is self-trusting but
not self-installing. See [subsystems/packages.md](subsystems/packages.md).

## Capture a new portable dotfile

**When:** you made a deterministic user-preference change you want on every
machine — an editor config, a tool's rc file, a theme.

1. Make the change in the live file under `$HOME` and confirm it works.
2. Add exactly one line to `tooling/data/dotfiles.manifest`. The columns are
   `kind|live path relative to $HOME|chezmoi source path|file pattern`:

   | Kind | Use for |
   |---|---|
   | `copy` | a single static file |
   | `template` | a file with a chezmoi template; the `.tmpl` is hand-maintained and `just sync` leaves it alone |
   | `directory` | every matching file one level deep, e.g. `*.fish` |
   | `tree` | a whole subtree, e.g. a skills directory |
   | `scrub` | a mixed file that must pass through a filter under `tooling/scrub/` first |
   | `scaffold` | image-owned, applied by chezmoi, never captured from live |

3. Name the source path the way chezmoi does. Real lines from the manifest:

   ```text
   copy|.config/lazygit/config.yml|dot_config/lazygit/create_config.yml|-
   copy|.local/bin/workstation-dev|private_dot_local/bin/create_executable_workstation-dev|-
   copy|.config/btop/btop.conf|dot_config/btop/create_btop.conf|-
   ```

   `create_` is what makes the seed create-only, so an existing user edit wins
   over the image default. Use it for every personal file.
4. `just sync` to generate the seed from live.
5. Read `git diff` before anything else: credentials, absolute home paths,
   machine-specific state, generated noise.

**Verify:**

```bash
just sync
git diff
just validate
```

`tooling/dotfiles/validate-manifest` diffs the manifest's expected inventory
against every file actually present under the seed tree, and rejects a duplicate
live or source path. A file that exists in the tree but not in the manifest
fails, and vice versa. Full workflow in
[capturing-changes.md](capturing-changes.md).

Never capture `fish_variables`, mutable DMS JSON, Neovim state or cache, backup
files, browser profiles, histories or auth stores. If the file mixes portable
config with secrets, give it a `scrub` filter rather than a `copy` entry — see
[subsystems/ai-clis.md](subsystems/ai-clis.md).

## Add a systemd unit

**When:** the image must run something — a boot-time helper, a per-login seed,
a timer.

1. Name it `workstation-<concern>` and put it at
   `system_files/usr/lib/systemd/system/` (system scope) or
   `system_files/usr/lib/systemd/user/` (user scope).
2. **A user unit needs `ConditionUser=!@system`**, or it also runs in the
   greeter's user manager against a read-only home and fails on every login
   screen — [conventions.md](conventions.md) has the why. Our own units carry it
   inline:

   ```ini
   [Unit]
   ConditionUser=!@system
   ```

   For an RPM-owned unit you enable globally, the condition goes in a drop-in at
   `system_files/usr/lib/systemd/user/<unit>.d/NN-<concern>.conf`. Never call a
   drop-in `override.conf` — that is the name `systemctl edit` writes, and it
   replaces rather than merges.
3. "Not ready yet" is an `ExecCondition`, never a non-zero `ExecStart`. The
   second reports a failed unit forever.
4. Add one `enable <unit>` line to
   `system_files/usr/lib/systemd/system-preset/10-workstation-os-image.preset`
   or the matching `user-preset/` file. Do not touch `build_files/50-services.sh`
   — it derives its `systemctl preset` arguments from those files
   (`mapfile -t system_units < <(sed -n 's/^enable //p' "$system_preset")`), so
   the preset is the single list of enablement intent. Only explicit *disables*
   are written by hand there, because a preset cannot undo an enablement symlink
   another layer already wrote.
5. If the unit needs a directory or a compatibility symlink under `/var`,
   create it with a tmpfiles entry instead of letting the build bake one in.
   Add one file per feature to `system_files/usr/lib/tmpfiles.d/`, named
   `NN-workstation-<feature>.conf`. Content that ships inside the image under
   `/var` is applied at initial provisioning and never on upgrade, so it stays
   frozen at whatever the first deploy wrote; bootc's `var-tmpfiles` check flags
   it, and the Containerfile's final `bootc container lint --fatal-warnings`
   turns that warning into a failed build. `99-workstation-dms-greeter.conf` is
   the worked example — greetd's `%post` masks a portal unit under
   `/var/lib/greetd`, and the tmpfiles entries recreate the mask on every boot.
6. Add the gate. `build_files/99-check-build.sh` runs `systemd-analyze verify`
   over three globs — `/usr/lib/systemd/system/workstation-*.service`,
   `/usr/lib/systemd/user/workstation-*.service` and
   `/usr/lib/systemd/user/workstation-*.timer` — plus four third-party user
   units named one by one (`fcitx5.service`, `iio-niri.service`,
   `udiskie.service`, `dsearch.service`). A new `workstation-*` service in
   either scope, or a user timer, is covered automatically. **A system-scope
   timer, a socket, or a further third-party unit is not** — add it to that
   argument list by hand.

**Verify:**

```bash
just build   # asserts every preset `enable` produced an /etc symlink,
             # and that every non-workstation user unit has the ConditionUser drop-in
just audit   # tooling/audit/units checks the LIVE machine against the same presets
```

The two are not interchangeable. The build gate proves the image; only
`tooling/audit/units` catches a local `systemctl mask`, which is how
`uupd.timer` was once found masked with its `.wants` symlink still intact
underneath. See [validation-and-gates.md](validation-and-gates.md).

## Ship an image-owned file into `/etc`

**When:** a package reads its configuration only from `/etc` and you want the
image to own the default.

`/etc` is a three-way ostree merge, so a file shipped at `system_files/etc/` is
frozen the moment anything rewrites it locally. The factory pattern keeps the
content in `/usr` instead, where updates always land; the merge semantics behind
it are in [conventions.md](conventions.md).

Worked end to end, using the file this image actually ships:

1. Put the content under `system_files/usr/share/factory/`, mirroring the
   absolute path: `system_files/usr/share/factory/etc/xdg/xdg-terminals.list`.
2. Add a tmpfiles file, one per feature —
   `system_files/usr/lib/tmpfiles.d/10-workstation-terminal.conf`:

   ```text
   L+ /etc/xdg/xdg-terminals.list
   ```

   With the argument omitted, `systemd-tmpfiles` links to the file of the same
   name under `/usr/share/factory/`, so the target never has to be spelled out.
3. If the parent directory is not owned by another package, create it in the
   same file. `10-workstation-docker.conf` needs
   `d /etc/docker 0755 root root -` before its `L+`; the terminal file needs
   nothing, because `/etc/xdg` is owned by the `filesystem` package.
4. Choose the suffix deliberately. `L+` removes and replaces whatever already
   exists at the path, so `/etc` is not where a local override of that file can
   live. Plain `L` creates only if absent — which means anything that repoints
   the path at runtime outlives every image after it. That is why
   `99-workstation-dms-greeter.conf` uses `L+`: it had plain `L` so `dms greeter
   sync` could repoint the greeter's theme files at the user's own, and one of
   those files later became unreadable to the greeter and cost a graphical
   login.
5. If the file has a validator, run it in `99-check-build.sh` against the
   factory copy, not the `/etc` path — tmpfiles runs at boot, so the symlink
   does not exist during the build:
   `dockerd --validate --config-file=/usr/share/factory/etc/docker/daemon.json`.

A handful of files legitimately ship straight to `system_files/etc/` — the
greetd config and its niri chain, `etc/default/useradd`, the signing public key.
Those are audited instead: `tooling/audit/etc-drift` diffs every file under
`system_files/etc/` against `/usr/etc` on the booted deployment and reports any
that the machine has diverged from or deleted.

**Verify:**

```bash
just build   # systemd-tmpfiles --dry-run --create catches a malformed L or d line
just audit   # on a deployed machine: Image-owned /etc drift
```

## Add or reclaim a niri keybind

**When:** you want a new shortcut, or you want a key back that DankMaterialShell
has taken.

niri resolves duplicate binds **last-definition-wins**, silently, and
`niri validate` still exits 0. `~/.config/niri/config.kdl` includes the image
config, then `dms.kdl`, then `local.kdl`, so `local.kdl` is the only include that
outranks the DMS-generated fragment. The full include order is in
[subsystems/desktop-session.md](subsystems/desktop-session.md).

For a key DMS does not claim:

1. Add the bind to `system_files/usr/share/workstation-os-image/niri/includes/binds.kdl`
   if it should ship with the image, or to `~/.config/niri/local.kdl` if it is
   personal.
2. `99-check-build.sh` resolves every `spawn` target in the image's includes, so
   a bind pointing at a program that is not installed fails the build.

For a key DMS claims:

1. Reclaim it in `~/.config/niri/local.kdl`:

   ```kdl
   binds {
       Mod+M hotkey-overlay-title="Maximize Column" { maximize-column; }
   }
   ```

2. Drop it from
   `system_files/usr/share/workstation-os-image/niri/includes/binds.kdl` — a key
   present in both that file and `~/.config/niri/dms/binds.kdl` is a bind the
   fork defines and DMS silently overrides, which `tooling/audit/niri-binds`
   fails on.
3. Or release the key on the DMS side instead: `dms keybinds remove niri <key>`.
4. To make the reclaim the default for a new account, hand-edit
   `system_files/usr/share/workstation-os-image/dotfiles/dot_config/niri/create_local.kdl.tmpl`.
   It is a `template` manifest entry, so `just sync` deliberately leaves it
   alone.

> Never hand-edit `~/.config/niri/dms/binds.kdl` or any other `dms/` fragment.
> DMS regenerates them at runtime and your edit disappears without a trace.

**Verify:**

```bash
just audit   # the "Niri bind ownership" section runs tooling/audit/niri-binds
niri validate -c "$HOME/.config/niri/config.kdl"
```

`tooling/audit/niri-binds` asserts three things `niri validate` cannot: that
`local.kdl` is still the last include, that no system bind is shadowed by the
DMS fragment, and that `maximize-column` is still reclaimed. See
[subsystems/desktop-session.md](subsystems/desktop-session.md).

## Promote a DMS preference to a workstation default

**When:** you changed something in the DMS GUI and want it to be how a fresh
account starts.

DMS settings are UI-owned after their one-time seed, so the repo tracks a small
reviewed overlay rather than the whole settings file.

1. Make the change in the DMS UI and confirm it behaves.
2. Review and select it:

   ```bash
   just dms-capture                  # fzf picker over portable deviations
   just dms-capture --list           # non-interactive: show what is on offer
   just dms-capture --select <key>   # capture one key by name, repeatable
   ```

   Select only values that should be workstation defaults. Never capture the
   complete settings file or runtime state.
3. The overlay is written to
   `system_files/usr/share/workstation-os-image/dms-settings.json`. Read the
   diff before committing.
4. To stop tracking a key: `just dms-remove`.

**Verify:**

```bash
just audit   # "Captured DMS preference defaults"
```

That section reports two independent signals: whether the tracked values still
match live, and whether portable deviations remain uncaptured. Both matter — a
tracked key whose live value has drifted is not noise. Restoring the overlay
into a live account is the destructive direction and is confirmed:
`just dms-apply`. Full workflow in
[capturing-changes.md](capturing-changes.md).

## Add a language to the Neovim IDE

**When:** you start working in a language whose LSP, parsers and formatters
Neovim does not yet set up.

Language extras are scoped to the project, not loaded globally: `dev nvim`
detects the languages host-side and passes them in `NVIM_MASON_LANGS`, so a
container gets only its own language servers and tools.

Edit the **live** files under `$HOME`. All three are manifest-captured, so the
repo seeds under `system_files/usr/share/workstation-os-image/dotfiles/` are
generated and `just sync` overwrites whatever you type into them.

1. Add the detector to `~/.config/fish/functions/dev.fish`, next to the existing
   ones. It appends a short key to `mlangs`:

   ```fish
   test -f "$root/go.mod"; and set -a mlangs go
   ```

2. Add the key to the gated import list in
   `~/.config/nvim/lua/config/lazy.lua`. Left is the key `dev.fish` emits, right
   is the LazyVim extra module name — they differ where LazyVim's name is longer
   (`ts` maps to `typescript`):

   ```lua
   { "go", "go" },
   ```

3. If you also add a user plugin under `~/.config/nvim/lua/plugins/` that
   configures a language server, gate it on the scope module, or it reinstalls
   that language's tooling in a container scoped to another:

   ```lua
   if not require("config.scope").has("go") then
     return {}
   end
   ```

4. `just sync` to capture all three into their `create_` seeds.

Never re-add a LazyVim extra ungated — disabling only the LSP server still
leaves the treesitter parser and the mason tools installing. Never edit
`create_lazyvim.json`.

**Verify:**

```bash
just validate   # compile-checks every nvim Lua seed with the image's own Neovim
cd <a project in that language> && dev nvim
```

See [subsystems/dev-environment.md](subsystems/dev-environment.md).

## Rotate the cosign signing key

**When:** the private key is compromised, or on a deliberate rotation schedule.

Do not improvise this. The policy entry is a `keyPaths` array, so a rotation
takes **two releases and never a flag day**: a machine that trusts only the old
key must already trust the new one before anything is signed with it, or it
cannot pull the release that would have taught it. `build_files/40-signing.sh`
picks up `workstation-signing-backup.pub` automatically for exactly this.

The full procedure, both releases and the CI secret, is in
[supply-chain.md](supply-chain.md). Note that `tooling/validate/image-build`
compares `cosign.pub` against
`system_files/etc/pki/containers/workstation-signing.pub` and fails if they
differ, so a half-finished rotation cannot pass — which is the point.

## Onboard a repository for worktree file propagation

**When:** a repo's worktrees need its untracked local files — `.env`,
`.idea/`, `.claude/settings.local.json`.

`init.templateDir` already seeds the post-checkout hook into freshly cloned
repos. This is the retrofit for repos that already exist.

```bash
cd <repo> && just worktree-init          # the current repo
just worktree-init ~/projects/foo ~/projects/bar
just worktree-init --all                 # every repo under ~/projects
```

`--all` walks `WORKSTATION_PROJECTS_ROOT` (default `~/projects`) to a depth of
four, skipping `node_modules`, `vendor` and existing worktree directories. It is
idempotent: it never overwrites an existing `.worktreeinclude`, and never
replaces a hook it does not recognise as its own. It *does* replace an older
version of its own hook — `hook: upgraded (v0 -> v3)` — which is how a change to
the hook reaches repos that already have one.

A repo carrying a third party's `post-checkout` (git-lfs writes one) is reported
as `hook: skip (a different post-checkout hook is already installed)` and left
alone, so it keeps only the second, machine-local net. Deal with the foreign hook
first, then re-run. For a stale `git lfs install` with nothing actually tracked in
LFS, that means deleting `.git/hooks/post-checkout` and `.git/hooks/post-merge`
and unsetting `lfs.repositoryformatversion`; the managed hook chains git-lfs
itself, so a repo that genuinely uses LFS loses nothing by handing the slot over.

**Verify:**

```bash
hook="$(git rev-parse --git-common-dir)/hooks/post-checkout"
test -x "$hook" && head -2 "$hook" | tail -1     # the ownership sentinel and its version
cat .worktreeinclude
```

Every creation path — herdr, an agent, a raw `git worktree add` — reaches the
same committed `.worktreeinclude` through the hook.
Never add a second copy list. See
[subsystems/dev-environment.md](subsystems/dev-environment.md).

## Housekeeping

**Prune orphaned Flatpak runtimes.** uupd updates Flatpaks but never prunes them
— it has no such option — so runtimes accumulate as apps change or are removed.
This deletes data, so it is interactive and confirmed rather than wired into the
nightly update path:

```bash
just flatpak-prune
```

**Clean tool byproducts out of the checkout.** `gitleaks dir .` does not respect
`.gitignore`, so anything left in the working tree is inside the secret-scan
surface. Run this before `just validate` or before opening a PR:

```bash
just clean
```

It removes the local `review-` images and the untracked byproducts AI tool
installers drop in the working directory, mirroring `.gitignore` and
deliberately going no further.

Update, verify, roll back, recover and the rest of the housekeeping recipes are
in [operating.md](operating.md).

## Before you open a pull request

Run these in order from the checkout:

```bash
just audit      # deployment layers, undeclared packages, uncaptured personal
                # state, image-managed config drift — needs the live machine
just sync       # refresh the create-only seeds from live
just ai-bundle  # ONLY if you touched an AI CLI seed; see below
git diff        # credentials, machine paths, generated noise, stray packages
just validate   # every gate that can run here
just build      # image changes only
```

`just capture` bundles `sync`, `validate` and the diff into one recipe. It has
no `ai-bundle` step between `sync` and `validate`, so if your change touched a
seed under `dot_claude/`, `dot_codex/` or `dot_config/opencode/`, the
`tooling/ai/build-ai-cli-bundle --check` assertion inside `validate` will fail
against a stale bundle. Run the steps by hand in that case.

**Why the local run is not optional.** `tooling/validate/all` needs a live
workstation — a booted deployment, an installed DMS, `$HOME`, foot — so CI never
reaches it. The dotfile manifest check, the AI reset tests, the AI bundle check,
the fish parse and `tooling/audit/workstation` run only where you run them. CI
proves the rest: which job runs which gate, and which paths decide whether the
image is rebuilt at all, are in [build-and-ci.md](build-and-ci.md); which
assertion covers the image versus the machine is in
[validation-and-gates.md](validation-and-gates.md).

Commits follow Conventional Commits with a scope: `fix(build):`, `feat(audit):`,
`docs(niri):`. Use a branch and a pull request for anything durable, and never
leave a requested permanent workstation change only on the live machine.
